## 13. 추가 보완 명세 — AR 정합·상태 관리·복구 계약

본 장은 v0.3의 구성요소와 역할 분담을 유지하면서 구현 과정의 모호함을 보완한다. 기존 본문·상태 전이표·JSON 예시가 본 장과 충돌하면 **본 장을 우선 적용**한다.

### 13.1 좌표계 및 마커 포즈 처리

#### 좌표 변환 절차

마커 검출기가 반환하는 포즈를 곧바로 ARFrame의 포즈로 사용하지 않는다. 다음 순서로 처리한다.

1. 검출기의 좌표축·회전·단위를 프로젝트 좌표계로 변환한다.
2. 검출에 사용한 영상 시점의 카메라 AR 포즈와 합성한다.
3. ARFrame에서 표현한 마커 포즈를 구한다.
4. 지도에 저장된 마커 포즈와 비교하여 MapFrame→ARFrame 정합을 계산한다.

검출 영상과 카메라 포즈에는 동일한 프레임 식별자 또는 대응 가능한 촬영 시각을 사용한다. 검출 완료 시점의 최신 카메라 포즈를 촬영 당시 포즈 대신 사용하지 않는다.

ARFrame의 직렬화 기준은 **미터 단위의 AR 세션 좌표**로 고정한다. Unity world 좌표를 사용한 값은 XR Origin 변환을 제거하거나, 동일한 기준으로 변환한 뒤 처리한다.

#### 마커 설치 및 지도 데이터

MVP의 마커는 **벽에 수직으로, 인쇄물의 위쪽이 위를 향하도록** 설치한다. 이 제약을 만족하는 경우 지도 포즈는 기존의 `position`과 `yaw_deg`로 표현한다.

- `position`: 마커 중심의 MapFrame 좌표
- `yaw_deg`: 마커 앞면이 바라보는 수평 방향
- 마커 기준축: 위쪽은 `+y`, 앞면 바깥쪽은 `+z`
- `marker_size_m`: 선택한 검출기가 요구하는 검출 영역의 실제 한 변 길이
- 설치 방향·크기·측량값은 현장 데이터와 함께 기록한다.

기울어진 벽, 바닥, 천장 등에 설치하는 경우에는 전체 회전 정보를 저장하는 스키마로 확장한다. 이 경우 위치와 yaw만으로 마커 포즈가 완전히 표현된다고 가정하지 않는다.

기존 역할표의 “마커 6DoF 포즈”는 MVP에서는 **설치 제약이 있는 마커 위치·방향 측량값**으로 해석한다.

정합 공식은 기존 2.3을 사용하되, 계산된 yaw는 `[0, 360)`으로 정규화한다.

### 13.2 앵커·정합 품질·추적 복구

#### 앵커 유지

정합한 지도 콘텐츠는 ARAnchor 또는 검증된 추적 대상의 좌표를 기준으로 유지한다. 단순히 최초 변환값을 일반 GameObject에 저장하는 것으로 정합 유지 구현을 완료하지 않는다.

앵커 갱신에 따라 지도 콘텐츠의 변환을 갱신하며, 변환을 중복 적용하지 않도록 지도 루트의 부모·자식 관계를 고정한다.

#### 렌더 허용 조건

바닥 고정 화살표는 다음 조건을 모두 만족할 때 표시한다.

- 현재 AR 세션과 정합의 `ar_session_id`가 같다.
- 현재 지도 버전과 정합의 `map_version`이 같다.
- 현재 층과 정합의 `floor_id`가 같다.
- 단말 추적 상태와 앵커 상태가 유효하다.
- 정합 품질이 QA가 검증한 기준을 통과한다.
- 정합의 유효 거리·유효 시간 범위를 벗어나지 않았다.
- 표시할 경로가 현재 목적지와 지도 버전에 대응한다.

서버에 정합 기록이 저장됐는지는 렌더 허용 조건에 포함하지 않는다.

#### 오차 필드의 의미

`alignment_error_m`, `alignment_error_deg`에는 다음 중 하나로 구한 값을 기록한다.

1. 정합에 사용하지 않은 측량점·마커를 이용한 검증 오차
2. QA가 실제 공간 오차와의 관계를 검증한 추정 방식의 결과

검출기 잔차를 검증 없이 공간 오차로 간주하지 않는다. 픽셀 단위의 잔차는 미터 단위 필드에 넣지 않는다.

`error_method`에는 사용한 측정·추정 방법을 식별할 수 있는 값을 기록한다. 오차를 측정하거나 검증된 방식으로 추정할 수 없으면 품질 미확인으로 처리하고 2D 안내를 사용한다.

QA는 기존 오차 임계값과 함께 다음 항목을 확정한다.

- 정합 지점에서의 유효 이동 거리
- 재검증 또는 재정합이 필요한 시간
- 허용 가능한 마커 관측 거리·각도
- 앵커 갱신 및 추적 복구 후의 재사용 기준

#### grace 이후 복구

`tracking_grace_s` 이내에 추적이 복구돼도, 시간과 `ar_session_id`만으로 기존 정합을 재사용하지 않는다.

동일 AR 세션, 앵커 유효성, 정합 품질 기준을 모두 확인한 경우에만 렌더를 재개한다. 확인되지 않거나 AR 세션이 리셋되면 정합을 무효화하고 재정합을 요청한다.

참고: [Unity 앵커 설명](https://docs.unity3d.com/Packages/com.unity.xr.arfoundation@6.1/manual/features/anchors/introduction.html), [AprilTag 포즈·좌표계 설명](https://github.com/AprilRobotics/apriltag#pose-estimation)

### 13.3 정합 리소스와 서버 동기화

#### 정합 식별 및 유효 범위

앱은 정합을 새로 계산할 때 `alignment_id`를 UUID로 생성한다.

정합의 유효 범위는 다음 조합으로 식별한다.

`map_id + map_version + ar_session_id + floor_id + alignment_id`

같은 물리적 정합을 유지한 채 경로만 재계산하는 경우에는 정합을 다시 생성하지 않는다. 마커 재정합으로 기준 변환을 새로 계산하면 새 `alignment_id`를 발급한다.

`POST /ar-alignments`의 변경 사항은 다음과 같다.

| 필드 | 규칙 |
|---|---|
| `alignment_id` | 필수. 앱이 생성한 정합 식별자 |
| `map_version` | 필수. 정합에 사용한 지도 버전 |
| `ar_session_id` | 필수. 정합에 사용한 AR 세션 |
| `floor_id` | 필수. 정합이 유효한 층 |
| `measured_at` | 필수. 정합 계산에 사용한 관측 시각 |
| `route_id`, `route_revision` | 선택. 진단용 정보이며 정합 유효성의 기준으로 사용하지 않음 |

동일 정합의 재전송은 같은 `alignment_id`와 멱등성 키를 사용한다. 서버 응답은 동일한 `alignment_id`를 반환한다.

#### 재탐색 전 동기화

렌더는 단말에서 판단하되, `start.type = "map_position"` 경로 요청 전에 해당 정합 기록의 서버 저장을 확인한다.

- 정합 기록이 아직 동기화되지 않았으면 먼저 기록을 전송한다.
- 전송 중에도 단말의 정합이 유효하면 기존 경로 렌더는 유지할 수 있다.
- 서버는 기록 미동기화와 실제 정합 무효를 구분한다.

오류를 다음과 같이 구분한다.

| 코드 | HTTP | 의미 | 앱 대응 |
|---|---:|---|---|
| `ALIGNMENT_NOT_SYNCED` | 409 | 요청한 정합 기록이 서버에 없음 | 정합 기록 전송 후 경로 재요청 |
| `ALIGNMENT_REQUIRED` | 409 | 정합이 무효이거나 지도·층·AR 세션이 맞지 않음 | 2D 전환 및 재정합 |

정합 기록 미동기화만을 이유로 사용자에게 마커를 다시 비추도록 요구하지 않는다.

### 13.4 출발 위치와 경로 연결

#### 마커 확인 시 실제 위치

마커가 연결된 `node_id`는 주변 위치를 나타내는 참조값이다. 마커를 관측한 사용자의 실제 위치와 동일하다고 간주하지 않는다.

정합에 성공하면 현재 카메라 AR 위치를 MapFrame으로 역변환한다.

```text
p_map = inverse(R_y(yaw_deg)) · (p_ar_camera − translation_m)
```

보행 경로에 사용하는 위치는 다음과 같이 정의한다.

- `x`, `z`: 역변환한 현재 카메라 위치의 수평 좌표
- `y`: 현재 층의 바닥 높이 `elevation_m`
- `heading_deg`: 지도 기준 카메라의 수평 시선 방향

마커 방식의 `/location-confirmations` 요청에는 기존 필드에 다음 정보를 추가한다.

- `map_version`
- `alignment_id`
- `position_map_m`
- `heading_deg`

서버는 마커·층·지도 버전과 값의 형식을 검증한다. 물리적 정확도는 단말 검증과 QA 측정이 판단한다.

마커로 정합한 경우 최초 경로에도 `start.type = "map_position"`을 사용할 수 있다. 사진 후보·수동 선택으로 노드만 확정한 경우에는 기존 `confirmed_node`를 사용한다.

`map_position` 요청에는 기존 필드 외에 `alignment_id`를 포함한다.

#### 경로 그래프 연결

현재 위치는 단순히 가장 가까운 노드로 이동시켜 처리하지 않는다. 같은 층의 보행 가능한 엣지에 연결하고 다음을 확인한다.

- 최대 연결 거리 이내인지
- 연결선이 벽이나 통행 불가 구역을 통과하지 않는지
- 현재 위치에서 해당 엣지에 실제로 접근할 수 있는지

검증할 데이터가 없거나 연결 후보가 모호하면 자동 연결을 보류하고 위치 재확인을 요청한다.

곡선 통로·계단참·방향 전환 지점에는 중간 노드를 배치하여, waypoint 사이의 직선이 실제 보행 경로를 벗어나지 않게 한다. 경로 응답에는 현재 위치에서 그래프 연결점까지의 이동 구간도 포함한다.

### 13.5 세션 상태 전이 보완

경로 계산과 안내 시작을 구분한다. 복구 후에도 경로 계산 성공만으로 자동으로 `navigating`으로 전환하지 않는다.

| 현재 state | 요청·조건 | 다음 state 및 처리 |
|---|---|---|
| `needs_confirmation` | `/localizations` 재촬영, 후보 있음 | `needs_confirmation`, 이전 후보 대체 |
| `needs_confirmation` | 재촬영 결과 `no_match` | `needs_location`, 이전 후보 폐기 |
| `relocalization_required` | 위치 확정 | `ready_to_navigate` |
| `ready_to_navigate` | `/routes`, 최초 생성 또는 재탐색 | `ready_to_navigate`, 활성 경로 갱신 |
| `ready_to_navigate` | 유효한 활성 경로에 대한 `navigation_started` | `navigating` |
| `navigating` | 동일 목적지 재탐색 성공 | `navigating`, 경로 revision 증가 |
| `navigating` | 이동을 요구하지 않는 정보 질문 | 기존 목적지·경로·state 유지 |
| `failed` 이외 상태 | 새 목적지 확정 | 이전 경로 해제 후 위치 유효성에 따라 `ready_to_navigate` 또는 `needs_location` |
| `failed` 이외 상태 | 목적지 불명확 | `needs_clarification`, 새 경로 시작 보류 |
| 모든 상태 | 현재 요청에 해당하는 `navigation_cancelled` | `idle`, 목적지·경로·대기 중 AI 작업 무효화 |

복구 시퀀스는 다음으로 통일한다.

`위치 재확인 → ready_to_navigate → 경로 갱신 → navigation_started → navigating`

새 목적지에 사용할 현재 위치는 유효한 정합에서 얻은 최신 위치 또는 새로 확인한 위치여야 한다. 과거 시작 노드를 현재 위치로 무조건 재사용하지 않는다.

동일 목적지의 재탐색은 기존 `route_id`를 유지하고 `route_revision`을 증가시킨다. 목적지 변경 또는 취소 후 새로운 안내를 시작하면 새 `route_id`를 발급한다.

### 13.6 동시 요청·지연 응답·이벤트 처리

#### 상태 변경 보호

기존 API 외에 `/messages`, `/localizations`에도 `expected_revision`을 필수로 추가한다.

Backend는 다음 규칙을 적용한다.

1. 요청 접수 시 revision을 확인한다.
2. 오래 걸리는 AI·비전 호출 동안 세션 잠금을 유지하지 않는다.
3. 결과 반영 직전에 revision과 해당 작업의 유효성을 다시 확인한다.
4. 취소·목적지 변경·새 위치 확인 등으로 문맥이 바뀌었으면 결과를 상태에 반영하지 않는다.
5. 이전 작업 결과를 폐기한 경우 `409 REQUEST_SUPERSEDED`와 현재 세션 상태를 반환한다.

같은 종류의 AI 작업을 새로 접수하면 이전 대기 작업을 무효화한다. 앱은 `/messages`, `/localizations` 각각에 증가하는 `operation_seq`를 보내며, 서버는 더 낮은 순번의 지연 요청·결과를 적용하지 않는다.

멱등성 키는 중복 실행 방지에 사용하며, 상태 충돌이나 요청 순서 제어를 대신하지 않는다.

#### 이벤트 순서 및 적용 대상

이벤트에는 다음 정보를 포함한다.

- `event_id`
- `event_seq`: 해당 세션에서 증가하는 이벤트 순번
- `route_id`, `route_revision`: 경로 관련 이벤트
- `ar_session_id`, `alignment_id`: 추적·정합 관련 이벤트
- `client_timestamp`

단말은 이벤트 순번을 세션 동안 유지하고, 이벤트 배치를 순서대로 전송한다. 서버는 수신 순서나 단말 시각 대신 `event_seq`를 기준으로 처리한다. 앞선 이벤트가 누락되면 후속 이벤트의 상태 적용을 보류한다.

이전 경로·이전 AR 세션·이전 정합에 대한 이벤트는 진단 로그로 보관하되 현재 상태를 변경하지 않는다.

경로 생성 전 취소처럼 `route_id`가 없는 상태 변경 이벤트에는 `expected_revision`을 포함하여 오래된 취소가 새 작업에 적용되지 않도록 한다.

이벤트 응답은 저장과 상태 적용을 구분한다.

- `accepted_event_ids`: 저장한 이벤트
- `applied_event_ids`: 현재 상태에 적용한 이벤트
- `ignored_events`: 적용하지 않은 이벤트와 사유
- `pending_event_ids`: 순서 확인 등을 위해 적용을 보류한 이벤트
- `session`: 처리 후 state와 revision

앱은 오프라인 이벤트 동기화와 상태 재조회 후 최신 revision으로 재탐색 등 후속 요청을 보낸다.

### 13.7 층 변경·장애 대체·지도 버전

#### 층 변경

MVP에서는 경로의 층 전환 단계와 새 층 마커 확인을 조합해 현재 층을 판단한다. 카메라 높이 변화만으로 층을 확정하지 않는다.

- 층 전환 구간 진입 시 기존 층의 바닥 화살표를 숨긴다.
- 새 층이 확인되고 해당 층의 정합이 유효해질 때까지 2D 단계 안내를 표시한다.
- 층 이동만으로 세션 `state`를 변경하지 않는다.
- 새 층 확인과 정합 결과를 이벤트 및 정합 기록으로 보고한다.

#### 장애 대체

사용자가 `selected_poi_id`로 목적지를 직접 선택한 경우 Backend가 POI 존재 여부·지도 버전·`verified`를 직접 검증한다. 이 경로는 Agent·LLM 호출 없이 처리할 수 있어야 한다.

장애 상황의 안내 범위는 다음과 같다.

| 상황 | 동작 |
|---|---|
| AI 장애, Backend 정상 | 수동 목적지·위치 선택으로 진행 |
| AR 미지원 또는 정합 무효 | 확보한 경로의 2D 단계 안내 |
| 네트워크 단절, 경로 확보됨 | 저장된 경로와 단말 상태로 가능한 안내 유지, 서버 재탐색은 보류 |
| 네트워크 단절, 경로 미확보 | 경로를 받지 못했음을 표시하고 재시도 제공 |

2D 안내에서도 현재 위치·진행 단계를 확인할 수 없으면 마지막 확정 위치와 경로 요약을 표시한다. 확인되지 않은 이동 진행을 확정적으로 안내하지 않는다.

#### 지도 버전

세션은 하나의 `map_version`을 기준으로 동작한다. 그래프·POI·마커·위치 후보·정합·경로는 같은 버전을 사용한다.

- 그래프·POI 조회는 세션의 지도 버전을 지정할 수 있어야 한다.
- 내부 POI 검색에도 `map_version`을 전달한다.
- 위치 확인 요청은 후보·마커와 동일한 지도 버전인지 검증한다.
- 새 지도 배포만으로 진행 중인 세션을 조용히 다른 버전으로 변경하지 않는다.

기존 버전을 더 이상 사용할 수 없어 전환해야 하면 `MAP_VERSION_MISMATCH`와 `required_map_version`을 반환한다. 앱은 기존 후보·정합·경로를 무효화하고 지도 다운로드, 위치 확인, 경로 생성을 다시 수행한다.

### 13.8 추가 검증 항목

기존 11장의 검증에 다음 항목을 추가한다.

| 검증 항목 | 합격 조건 |
|---|---|
| 마커 좌표 변환 | 기기 방향을 바꿔 관측해도 지도 방향과 화살표 방향이 일치 |
| 이동 후 정합 | QA가 정한 유효 거리·시간 안에서 오차 기준 충족 |
| 단기 추적 복구 | 유효성을 확인한 경우에만 기존 정합으로 렌더 재개 |
| 취소 후 지연 응답 | 이전 AI·비전 결과가 목적지·위치·state를 복원하지 않음 |
| 이벤트 지연·중복·역전 | 이전 이벤트가 현재 경로·정합 상태를 덮어쓰지 않음 |
| 정합 기록 전송 지연 | 렌더와 서버 동기화를 구분하고, 미동기화 때문에 불필요한 재촬영을 요구하지 않음 |
| 마커에서 떨어진 출발 | 실제 사용자 위치에서 보행 가능한 경로로 연결 |
| 재위치 확인 후 복귀 | 경로 갱신과 시작 이벤트를 거쳐 `navigating`으로 복귀 |
| AI 장애 중 수동 선택 | Agent 호출 없이 검증된 목적지와 경로 설정 가능 |
| 지도 버전 전환 | 서로 다른 버전의 지도·정합·경로를 함께 사용하지 않음 |

각 결과에는 단말·앱·지도·프롬프트 버전, 입력 조건, 실제 결과, 실패 원인, 수정 및 재검증 내역을 기록한다.
