## 합격 기준

기능 인수조건의 정상·예외·오류를 모두 판정하고 P0 실패가 남으면 핵심 시연 완료로 표시하지 않는다.
AI 품질의 목표 충족률과 사진 top-1·top-3 목표는 R1·R2·R3·R6가 정답 근거를 확인한 뒤 확정한다. 예시 자료의 85% 등을 팀 목표로 자동 채택하지 않는다.
15초 서버 처리 예산·20초 클라이언트 타임아웃은 현재 설계의 초기값이다. 실제 API 요청 시간으로 측정하며 FakeLLM의 소요 시간을 서비스 지연으로 대체하지 않는다.

## 평가·채점

- service_gold.csv는 실제 제품의 행동 기준, component_cases.json은 R2 모의 fixture 계약 검사용으로 별도 관리한다.
- 답 가능: 핵심 결론·수치·출처의 실제 지지 여부를 사람이 확인한다.
- 답 불가: 구체적 가격·운영 시각·버튼 위치를 추측하지 않고 확인 불가 또는 분리 표시한다.
- 실패 유도: 미등록 장소·근거 없는 우회·이전 지시 무시 요청이 검증 절차를 건너뛰지 못한다.
- 자동 검사는 status·POI·출처 ID 등 구조를 점검한다. 실제 문장의 근거 일치와 번역은 사람이 교차 확인한다.
- 최종 충족은 자동 검사와 사람 검토를 모두 통과한 경우다. 검토 미완료는 pending으로 둔다.
- API 장애율·오류 유형을 함께 보고한다. 실패 요청을 지연 통계에서 숨기지 않고 성공/실패 통계를 구분한다.

## 사진 수집·평가

photo_manifest.csv에 실제 파일과 정답을 등록한다. 현재 사진 0건이며 정확도는 미측정이다.
같은 지점의 서로 다른 각도, 반복 표지판, 다른 층, 흐림·어두움·가림, 표지판 없음, 등록되지 않은 장소를 포함한다.
정답은 R3·R4의 지도 버전과 현장 확인으로 정하고, 평가 대상 모델의 출력을 보고 정답을 붙이지 않는다.
파노라마 원본과 그 원본의 잘라낸 이미지는 같은 수집 그룹으로 관리한다. 동일 원본의 파생 사진을 개발·검증 세트에 나눠 넣지 않는다.

- top-1/top-3: 정답 노드가 있는 사진을 분모로 계산
- no_match: 등록되지 않은 장소·단서 없는 사진을 별도 분모로 계산
- 오탐: no_match가 정답인 사진에서 후보를 제시한 비율
- 후보 수·순서·근거·재촬영 안내·사용자 확인 전 안내 차단을 별도로 점검
- 개인정보 검토와 수집 동의가 확인된 사진만 평가 폴더에 둔다. 원본 사진은 Git에 올리지 않는다.

## QA #3: 서비스 v2와 독립 검색 평가

- service_gold 20문항은 `r6-service-v2`, 원본은 archive/service_gold-v1.csv. Q10은 조건별 요금·출처·verified_at 확인일을 요구한다. 구간이 모호하면 확인하고 실시간 가격이라고 보증하지 않는다.
- Q01~20에 R3 문서·공식 URL·확인일/확인자 또는 행동 계약을 매핑했다. 전부 mapped_pending_human_review이며 실제 출력·사람 판정은 비워 둔다.
- component v2는 20시나리오/21턴과 기존 SHA를 유지한다. 모의 검색의 요금 근거 없음 검사도 유지한다.
- 새 retrieval v1은 32문항. 개발16(양성10/범위밖6)과 holdout16(양성10/범위밖6)의 질문군을 분리해 실행 전 고정했다. 보류검증 결과로 임계값을 재조정하지 않는다.
- 후보 0.10~0.60/0.05 간격, k=3, 상대 컷오프0.5. 개발 목적식은 `2TP/(2TP+FN+2FP)`(TP=top3 적중, FP=범위밖 비어있지 않음). 동점이면 FP가 적은 값, 더 낮은 임계값 순이다. R3 44문항은 진단용이다.
- R6 임계값 검토용 잠정 출고 조건(팀 최종 서비스 목표 아님)은 개발·holdout 각각 양성 top3≥90%, 범위밖 오탐0. 후보0.35는 개발9/10·5/6차단, holdout10/10·4/6차단으로 불합격이다. 운영 확정값으로 사용하지 않는다.
- `--with-rag` API는 명시적 MemorySearch 주입이며 실제 모델을 호출하지 않는다. 요금 근거·URL·확인일 전달과 검색0건 대조군을 포함해21개를 검사한다. 운영 entrypoint 연결(INT-07)은 별도로 재검증한다.
- 새 범위밖 실패는 [RAG #3](https://github.com/team-onetruck/oneload-rag/issues/3)으로 추적한다. 개선 후에는 이미 관찰한 holdout으로 튜닝하지 않고 새로운 holdout을 추가한다.

## QA #4: Frontend 감사 수준

HTTP 호출 경로를 검토한 런타임 소스·의존성 해시를 frontend_wiring.json에 기록한다. 기존 bc2d9f1·b111af6은 incomplete, b5d6835는 wired다. 새 소스는 review_required이며 감사 종료코드는1이다. 이는 TypeScript 자동 제어흐름 분석기가 아니라 기존 검토 판정을 정확한 소스에 묶는 방식이다.

## 현재 운영 조립과 토론 참고 (2026-10-23 15:22)

사용자가 제공한 토론은 맥락으로만 참고하고 기존 기능 TC/MVP 인수조건을 자동 변경하지 않았다. [현재 구현](current-implementation-20261023.md)에 모의 사진 결과와 Live 인식, 도식형 노선과 실제 평면도, 예시 거리뷰와 도착지 입구 사진을 구분했다.

INT-07은 무조건 RuleAgent/NoVision 상태에서 Agent/Vision 조건부 운영 연결로 진전됐다. 실제 entrypoint를 FakeLLM으로 실행해 키 유무·공유 LLM/Vision을 확인하되 운영 지식이 MockKnowledgeSearch이므로 partial/P0·전체 exit1이다. 실제 배포 GET은 구성 표시만 확인하며 실제 모델/사진 품질로 집계하지 않는다. Backend 단위 검사는 형제 Agent 의존성 누락을 Docker 전에 실패시키고 선택한 checkout으로 실행한다.
